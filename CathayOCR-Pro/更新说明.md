## 起点：v1.2.4（基线）

**修复除 Vulkan 外其它引擎全部不可用。**

**现象**：选择 ncnn Vulkan 以外的引擎（PP-OCRv6 ONNX / PP-OCRv5 / 经典版 / ncnn CPU / EasyOCR）时，引擎能正常启动、界面不报错，但处理完成后 `_result.txt` **只有文件头、正文 0 字**，导出的 `_layered.pdf` **没有任何文字层**。

**根因**：`PDFProcessor.ocr_consumer()` 每页识别第一步执行

```python
timeout_sec = self.ocr._instances[0].get_dynamic_timeout()
```

而 `get_dynamic_timeout()` **只定义在 `NcnnVulkanAdapter` 里**，基类与 Paddle / ncnn CPU 适配器都没有。于是选非 Vulkan 引擎时这一行立即抛 `AttributeError`；该调用**位于 try 之外**，OCR 消费线程当场死亡 → 该线程负责的页面永远不会被识别 → 结果为空。**（不是 v1.2.3 引入的：v1.1.3 加看门狗时只围绕 Vulkan 实现，所以在此之前除 Vulkan 外的引擎一直不可用。）**

**修复**：

1. **动态超时提升到基类** `OCREngineAdapter`（聚合所有活跃实例耗时样本，不足 3 个返回 180 秒，否则 p90×3 升档、上限 300 秒）；`NcnnVulkanAdapter` 保留自身实现，**Vulkan 行为零变化**；
2. **耗时记录下沉**：`PaddlePipeAdapter`、`NcnnCPUAdapter` 每页识别后记录耗时 → 「慢设备自动升档超时」对所有引擎生效；
3. **恢复能力补齐**：基类补默认 `restart()`（stop + start），看门狗对非 Vulkan 引擎的自动恢复不再静默失效；
4. **调用处加兜底**：`ocr_consumer` 取动态超时时用 `getattr` 判断可调用性。

**验证（真实 PDF 端到端）**：v6 CUDA / v5 Paddle CPU / 经典版 / ncnn CPU / EasyOCR 修复后分别出字 42 / 42 / 41 / 42 / 88 字，ncnn Vulkan 正常（逻辑未改动）。

> v1.2.4 也是 v1.3.x 的**引擎链路基线**。此后除 v1.3.0 一度改过、v1.3.1 又还原回来之外，
> 引擎调用方式、看门狗、双实例、超时策略、临时文件、请求派发、写回顺序**一直被刻意保持原样**。

### 2c. 引擎选择规则（简单模式最终版）

> 📘 完整规则（含专业模式、win7_v5 的 33 组 config 路由、Lite 差异、实测数据）见 `引擎规则说明.md`。

显卡档位由 4 档拆成 **6 档**。**NVIDIA 是否具备 CUDA 与显存大小无关**；AMD/Intel 没有 CUDA，分档**只影响「精度优先」时的边长**。

引擎决策分两条路径 —— 看勾选的语言里有没有带 ⚠ 的组：

| 路径 | 触发条件 | NVIDIA（≥12GB / ≤8GB） | AMD/Intel 独显 | 核显 / 纯 CPU |
|---|---|---|---|---|
| **普通路径** | 未勾选任何 ⚠ 组 | ≥12GB → **PP-OCRv6 CUDA**；≤8GB → **ncnn Vulkan** | **ncnn Vulkan** | **ncnn Vulkan**（模式切 **CPU**） |
| **⚠ 专用路径** | 勾选任一 ⚠ 组 | **西里尔（俄文等）→ PP-OCRv5 (Paddle CPU)**；其余 ⚠ 组 → **PP-OCRv6 引擎**（自动回退 v5 分语种模型，~3 秒/页） | **PP-OCRv5 (Paddle CPU)** | 同左 |

- **西里尔文为什么连 NVIDIA 也走 PP-OCRv5 (Paddle CPU)**：12 张俄文图实测，v6 引擎的 ONNX 路径会把 «Русский» 转写成 «Russkiy»；同款模型的 Paddle Inference 版（`win7_v5`）**12/12 全对**，且快约 5 倍（7.9s vs 42.3s）。两边本来就都在 CPU 上跑，所以换引擎**没有 GPU 性能损失**
- **≤8GB 为什么走 Vulkan**：Vulkan 显存占用低、可开双实例，批处理更快（约 2.2 页/秒，CUDA 约 1.1 页/秒）
- **v5 分语种模型目前走 CPU 推理**（ONNX Runtime 的 CUDA 内核对部分张量形状会报 Conv 运行期异常），速度与显卡档次无关（约 3 秒/页）

其余参数由「文档类型 + 精度档 + 显存档」决定：文档类型只决定**竖排检测 / 方向纠正**；
边长与渲染倍率由「精度档 + 显存档」统一决定（速度 / 标准 = 2240 + 2×；精度 = 大显存 2560 / 小显存 2240；
**只有「古籍竖排 + 精度优先 + 大显存或纯CPU」才用 3×**）；批处理数三档统一 **16**；
双实例除纯 CPU 档外默认开启。渲染倍率下拉文案 `2x` 改为 **`2x（高清）`**。

## v1.3.1 —— 引擎进程 / 通信链路还原老版（去托盘）

> **本版定位**：以 **v1.3.0 为基线**，把「引擎进程 / 通信链路」这一块**还原成长期稳定运行的老版（v1.2.3）行为**；
> 引擎选择 / 语言选择 / 出错保护层 / 日志 / 清理策略全部保留 v1.3.0 的成果。
> 另新增「输出目录说明」，并按你的要求**移除系统托盘**。

### 1. 引擎进程 / 通信链路还原为老版行为（核心改动）

| 项 | v1.3.0 行为 | v1.3.1 行为（= 老版） |
|---|---|---|
| `_ensure_running()` | 只看进程句柄活着就认为可用，从不探活 | **先做 1 秒 TCP 探活；探不通就地重启引擎**，并返回重启结果 |
| `_engine_is_ours()` 归属判定 | 有 | 无（老版没有这层判定） |
| `restart()` | `_proc_lock` 串行 + 8 秒抑制窗口 + 孤儿清理 | `stop(); sleep(0.5); start(params)` |
| `restart_single()` | 转 `restart_all()` | **真的只重启一个实例** |
| 请求派发 | `_dispatch_lock` 原子派发 | `self._adapter_index += 1`（无锁） |
| 临时 PNG | 每线程一份（`_thread_tmp_path`） | 每次请求新建 `NamedTemporaryFile` |
| 引擎 stdout / stderr | 都写 `engine_<端口>_stderr.log` | `stdout=DEVNULL, stderr=subprocess.PIPE` |
| 透明重发 | `_TCP_TX_RETRY = 2` | 无 |

**为什么要还原**：老版本长期稳定运行、从不发生「引擎中断」，顶多引擎卡住由看门狗把它重启掉。经取证，**两版引擎二进制与传给引擎的参数完全相同**，差异只在「主程序怎么对待引擎」。还原后，引擎的运行语义与老版一致。

**明确保留（不还原）**：语言 / 字典路由修复与引擎选择 UI、**出错保护层**（`_RESULT_OK_CODES = (100, 101)` 完整性闸门 + 三级恢复 + 警告文件 + 「取消 ≠ 完成」）、**按完整路径精确清理**引擎残留、运行日志窗口与日志落盘。

> 说明：v1.3.2 又把 `_ensure_running()` 改成「只检查、绝不起进程」，并把 `restart()` 换成 `_proc_lock` + 8 秒抑制窗 ——
> 但这一次的触发条件与老版「1 秒探活失败即重启」**不同**，正是为了根除「孤儿引擎」，见下一节。

### 2. 输出目录说明（新增）

输出目录框**不再回填上次路径**，默认**留空 = 输出到每个 PDF 自己所在的文件夹**；新增框内灰色占位提示、悬停 tooltip 与界面灰字说明。

> 老版会在启动时把上次的输出目录（如 `D:\OCR待AI处理`）自动填回输入框，看起来就像「默认输出到 D 盘那个文件夹」。本次已修掉。

### 3. 移除系统托盘（按要求）

## v1.3.2 —— 引擎层 3 处修复（界面一行未动）

现场日志（2026-10-10，第 134 / 136 / 139 册）显示：每一次「卡住」都是同一条链 —— **某页整整 180 秒没有响应** → 看门狗判定「引擎假死」→ 重启两个引擎 → 速度从 1.0 页/秒掉到 0.2 页/秒再慢慢爬回来。

### 1. 「孤儿引擎」——最主要的成因

`_ensure_running()` 原本是**「1 秒探活失败 → 直接再启动一个引擎进程」**。探活超时只有 1 秒，引擎忙时**必然失败**；而此时旧进程还在跑，重新启动会把旧进程引用覆盖掉——旧进程从此没人管，变成**霸占端口的孤儿**（日志里同一端口被连续启动两次）。之后请求随机打进孤儿：`connect` 成功、回复永远等不到 → `recv` 挂满 180 秒 → 看门狗重启 → 又生孤儿 = **周期性卡顿**。

**改法**：`_ensure_running()` 改成**只检查、绝不起进程**：

1. 自己的引擎进程句柄还活着 → 直接放行（探活失败只代表「忙」）；
2. 进程不在、但端口有人响应 → 不属于我们的占位者 → 清掉它；
3. 进程真死了 → 只清悬空引用，**不在这里重启**（重建统一交给看门狗）。

### 2. 「引擎不可用」与「真超时」分不开

引擎不可用时返回 `code=102, data="...timeout..."`，导致两者分不开；而消费端本来就按 `103` 写恢复分支，**那条路从来没走到过**。
**改法**：引擎不可用改为返回 `103`；`102` 只留给真超时与 TCP 错误。

### 3. 「并发重启抢同一端口」

两个 consumer 同时判定超时、同时调 `restart_all()` → 同一端口被连续启动两次。
**改法**：`restart()` 用**专用锁** `_proc_lock` 串行化 + **8 秒抑制窗**。该锁与 `self.lock` **分开**（后者会被卡在 `recv` 的线程持满 180 秒）。

**明确没改**：界面全部、完整性闸门 + 三级恢复、双实例轮询分页、动态超时（floor 180 / ceiling 300）、分页写回顺序。

**影响面（AST 逐符号核对）**：新增 `NcnnVulkanAdapter._engine_is_ours()` 1 个；修改 `__init__ / _tcp_request / _ensure_running / restart` 4 个；删除 0 个。
行为自检 T1~T5 全通过（用假进程对象，**不启动引擎、不碰显卡**）。

## v1.3.3 —— 并发竞态修复 + 日志语气分级

### 一、修复：临时图片「边写边读」竞态

**现象**：长时间批量识别时，日志间歇出现「某页连接被重置」（WinError 10053 / 10054），程序自动取回后继续。

**根因（两处叠加）**：

1. **轮询取号没有加锁**：`OCRClient.ocr_image_base64()` 里两个识别线程可能**同时读到同一个值** → 双双选中**同一个引擎实例**；
2. **写临时图片在锁外**：两个线程撞上同一实例时，一个线程会在**引擎正读取该 png 的同时覆写它** → 引擎读到半张图 → 连接被打断。

**修法**：`ocr_image_base64()` 取号与自增放进同一把锁（新增 `self._pick_lock`）。
**（Pro 的 `run_base64()` 本来就是每页独立临时文件，无此覆盖问题，故只补了取号加锁。）**

**影响面**：新增 0、删除 0；改动 `NcnnVulkanAdapter.__init__` / `OCRClient.ocr_image_base64` / `PDFProcessor.ocr_consumer`。引擎启停语义、双实例轮询策略、动态超时、完整性闸门、三级恢复、界面 —— **未改动**。

### 二、日志语气分级

按「**要不要用户操心**」分两档：单页连接瞬时中断 → **平实一句**（程序自动取回，无需用户做任何事）；
整页自动重试 → **不再单独刷一行**；真超时 / 引擎不可用 / 全文件重跑 / 跳过文件 → **保留告警语气**。
平实文案里**刻意不含** `error / 错误 / 失败 / 超时 / 重试 / 重启` 等会被日志窗口标红的关键字。

### 三、版本号

`v1.3.2` → `v1.3.3`：主程序文件头、窗口标题、关于框，以及启动器（`launcher_pro.py`）启动横幅。
（当时启动器 **exe** 未重新打包，内嵌横幅仍为旧值——已在 v1.3.5 重打包修正。）

## v1.3.4 —— 空白根源治理

**v1.3.4 = v1.3.3 + 引擎日志落盘 + 空白页引擎核验（探针）+ 日志语气平实化 + 两处追加收敛。**

### 1. 引擎「活着但已经废了」的怪病（空白文件的根源）

**铁证**：引擎日志里 `vkQueueSubmit failed -4` 出现 **6173 次**（-4 = `VK_ERROR_DEVICE_LOST`）；系统日志在故障时刻密集出现 `nvlddmkm ID=153`。

**机制**：Windows 的 TDR 机制默认给 GPU 命令 **2 秒**限时，超时就强制重置显卡驱动。驱动重置后 Vulkan 设备按规范**永久死亡**——但 ncnn 引擎不退出也不重建，于是进程活着、端口在、还照常回话，**只是每次计算都失败**，把每一页都报成「无文字」(101)。程序把这些页当正常空白放行 → 产出大量空白壳。

### 2. 两个配套修复（必须一起上才有效）

| 改动 | 作用 |
|---|---|
| **引擎日志落盘** | 原来引擎报错写进一根「没人读的管道」，写满约 4KB 就把引擎憋死，且崩溃原因全部丢失。现在落到 `ncnn\PPOCR-ncnn-Vulkan\engine_<端口>_stderr.log`（超 512KB 自动轮转） |
| **空白页引擎核验** | 只在引擎报「无文字」时，拿一张白底黑字图（「OCR TEST 12345」）问它一次，**连续两次认不出 = 引擎已废** → 自动重建引擎 + 重跑本页。正常书没有空白页，一次探针都不会发 |

### 3. 日志语气平实化

恢复类日志（重建引擎、重跑本页、整份文件重跑）改成平实的 `[自动恢复]` 语气。**只有一种情况保留红色告警：整份文件重跑用尽、被跳过并生成警告文件。**

### 4. 「连接瞬时中断」不再逐页刷屏

偶发的 TCP 连接重置（10053 / 10054）是**良性连接级抖动**——引擎进程全程活着、与 GPU 无关，程序立刻重发同一页就取回。现在改为**处理完一本书只汇总一行**：

```
[自动恢复] 本册共 23 页连接瞬时中断，均已自动取回（不影响结果）
```

有才打、没有不打。

### 5. 性能收敛：去掉 base64 中转（每页省一次编解码）

渲染线程原来要先 `base64` 编码放进队列，消费线程再解码回字节写临时图——**一来一回纯属多余**。
现在队列里直接放 **PNG 原始字节**：每页省一次编码 + 一次解码（约 17ms + 9ms）；在飞图片内存约 **10.2MB/页 → 7.7MB/页**；
**不改字节内容、不改识别结果**（等价性单测：新旧两条路交给引擎的字节逐字节相同）。

> **Pro 特例**：Paddle 系列引擎（管道协议只认 base64 文本）在**消费侧就地编码** —— 与旧行为**完全等价**，
> 只是把这一步从渲染线程挪到消费线程，总量不变。

### 改动清单（AST 级核对）

- **新增 8 个函数**：`_open/_close/_note/_read_stderr_log`（日志落盘 ×4）、`_get_probe_image_b64`、`_probe_extract_text`、`_probe_instance`、`_walk`（探针 ×4）
- **修改 6 个方法**：`__init__`（探针锁）、`_start_gpu`/`start`（日志落盘）、`ocr_image_base64`（101 时核验）、`ocr_consumer`/`process_pdf`（日志平实化）、`stop`（关句柄）
- **删除 0 个**；不碰看门狗语义、结果码定义、完整性闸门、动态超时、写回顺序、任何界面
- **日志收敛**：`process_pdf` 内新增本册计数器 `_tcp_jitter`，收成每册一行。**纯日志行为**
- **去 base64**：新增模块级 `_img_to_bytes()` 与 `_img_to_b64()`；渲染入队改传 `png_bytes`；`NcnnCPU/NcnnVulkan` 的 `run_base64` 改走 `_img_to_bytes()`；`PaddlePipeAdapter.run_base64` 对 bytes 入参就地编码。**纯数据管道改动**

## 附录 A：GPU 卡死 / 跑出大量空白（Windows TDR 超时）

> **不是软件坏了，是 Windows 的一条规则把显卡「误杀」了。**

Windows 有个「GPU 超时看门狗」（**TDR**）：只要显卡单个任务超过 **2 秒**没算完，系统就以为显卡死机了，**强制把显卡驱动重启一次**。驱动一重启，OCR 引擎手里的显卡就永久失效——**程序还在跑、界面也不报错，但每一页都算不出文字**，于是输出一堆空白。

**两个动作就能解决（建议都做）：**

1. **双击本目录的 `GPU卡死修复_调大TDR超时_需重启.reg`** → 弹窗点「是」→ **重启电脑**。这把 2 秒放宽到 8 秒。（反悔了？双击 `GPU卡死修复_还原TDR超时_需重启.reg` 再重启即可。）
2. **把「精度」改成 `FP16 (快速)`**（用 ncnn Vulkan 引擎时）。单次计算量大幅减少，更不容易撞上 2 秒线。**AMD 核显请保持 FP32。**

等价的注册表手工命令：

```
reg add "HKLM\SYSTEM\CurrentControlSet\Control\GraphicsDrivers" /v TdrDelay    /t REG_DWORD /d 8 /f
reg add "HKLM\SYSTEM\CurrentControlSet\Control\GraphicsDrivers" /v TdrDdiDelay /t REG_DWORD /d 8 /f
```

> **实测本机 TDR 相关键全部未设置**，即 Windows 默认的 **2 秒**。
> 副作用：万一显卡真的挂了，桌面最多卡 8 秒才恢复（原来 2 秒）。
>
> **换驱动不能保证解决**：TDR 是 Windows 的机制，与驱动版本无关。实测本机驱动 **610.74** 已是 RTX 5060 的适配版本，引擎确实跑在 `Vulkan device 1: NVIDIA GeForce RTX 5060`（r-score 76），**不存在「驱动装错 / 跑错卡」**。
>
> **v1.3.4 起程序还有兜底**：万一真撞上，会自动重建引擎 + 重跑本页，**绝不把「算不出来」当成「这页没字」交给你**。
