# CathayOCR Pro v1.3.0 更新说明

> 发布日期：2026-10-09

## 🎯 本次更新内容

### 1. 全新启动器 + 可独立、可吸附的运行日志窗口

新增 `CathayOCR Pro.exe` 瘦启动器（与 Lite 同代）：

- **双击即用**：不再弹黑框控制台，改为独立的「运行日志」窗口，实时显示启动过程、GPU 检测、识别进度与错误信息
- **关窗不打扰任务**：日志窗口随时可关，后台任务照常运行；可再次双击 exe 唤回**同一个**窗口（单实例互斥，不重复启动主程序）
- **吸附侧边栏模式**：可一键吸附到主程序右侧，自动收窄为侧边栏宽度（330px）并跟随主窗口移动
- **随主程序退出**：主程序关闭后日志窗口自动关闭；任务运行中主程序退出时日志窗保留以显示错误
- **防残留**：打包内嵌专属标记，启动时自动清掉自己上次遗留的 `%TEMP%\_MEI*` 解包目录，C 盘零残留
- 原 `启动.bat` 保留，作为备用启动方式

### 2. v5 语种识别真正可用 + 备选引擎全语种覆盖（重要修复）

此前在简单模式选择阿拉伯文/印地文/泰文等语种时，程序会切到 PP-OCRv5 引擎，但语言下拉**不会同步**（仍停在中文），导致这些语种实际用错误的模型识别、输出乱码。v1.3.0 修复并扩展：

- 选 v5 专属语种时，语言下拉自动同步；引擎按所选语言**自动路由到对应的官方分语种识别模型**
- PP-OCRv5 备选引擎现内置 **11 套官方分语种模型**（阿拉伯/天城文/泰/希腊/泰卢固/泰米尔/韩文/拉丁 40+ 语/东斯拉夫/西里尔 33 语/英文专用），覆盖全部 75 个语种选项
- 韩文改用官方 v5 专用模型（准确率 88%，旧 v3 模型仅 60.2%）
- **简单模式语言改为多选勾选（13 组）**：勾选文档中可能出现的语言（可多选），系统据此决定引擎；普通组只作提示不改引擎，带 ⚠ 的组（阿拉伯字母系/天城文系/泰/泰卢固/泰米尔/韩文/西里尔）会切换到专用分语种模型；专业模式仍保留完整 75 项
- 20 语种实测全部正确出字（含中/英/日零退化验证）

> ⚠️ 已知特性：阿拉伯文系（阿/波/维/乌）识别结果为镜像序（PaddleOCR 官方模型的字符输出顺序），字符本身识别正确；如遇此情况可自行反转文本顺序。

### 2b. 语言-引擎适配深度修正（字典逐字核对 + 实测修复）

对全部引擎的识别字典做了**逐字符核对**与实测，修正了一批"选了语言但引擎其实不认识"的隐藏问题：

- **重大修复：PP-OCRv6 (CUDA) 引擎的韩文/俄文识别**。此前 v6 引擎误将韩文/西里尔当作"内嵌支持"，实际官方 PP-OCRv6 单模型只覆盖 50 语种（中/繁/英/日 + 46 拉丁语系），导致选韩/俄时输出乱码。现修复为自动回退官方 PP-OCRv5 分语种模型（韩文 88% 准确率 / 东斯拉夫 / 西里尔），实测韩俄逐字正确
- **字典真相**：ncnn 引擎与 v6 引擎的通用字典（18709 字符，与官方 ppocrv6_dict.txt 逐行一致）不含阿拉伯文/天城文/泰文/韩文/西里尔/泰卢固/泰米尔——此前选这些语言在 ncnn/Vulkan 引擎下输出乱码且无任何提示
- **希腊文实测可用**：ncnn 字典含 76 个希腊字符，实测希腊文在 Vulkan 引擎识别正确，不再切换到专用模型
- **简单模式改为多选勾选**：勾选文档中可能出现的语言（13 组），系统自动决定引擎；带 ⚠ 的组（阿拉伯字母系/天城文系/泰/泰卢固/泰米尔/韩文/西里尔）勾选后自动切换到专用分语种模型，并在配置摘要中明示
- **专业模式开跑前守卫**：ncnn 引擎 + 不支持的语言组合会弹窗提醒，避免静默乱码
- **补齐 7 个字母系语言**：普什图文/信德文/克什米尔文/俾路支文（阿拉伯字母）与博杰普尔文/迈蒂利文/孔卡尼文（天城文），win7_v5 引擎语种路由扩至 33 组映射

### 2c. 引擎选择规则（简单模式，最终版）

> 📘 **完整规则（含专业模式、win7_v5 的 33 组 config 路由、Lite 差异、实测数据）见同目录 `引擎规则说明.md`。**

显卡档位由 4 档拆成 **6 档**（NVIDIA 与 AMD/Intel 各自按显存分大小两档 + 核显/纯CPU + 自动检测）。**NVIDIA 是否具备 CUDA 与显存大小无关**（本机 8GB 卡实测 CUDA 可用）；AMD/Intel 没有 CUDA，显示分档**只影响"精度优先"时的边长**。

**引擎决策分两条路径** —— 看勾选的语言里有没有带 ⚠ 的组：

| 路径 | 触发条件 | NVIDIA（≥12GB / ≤8GB） | AMD/Intel 独显 | 核显 / 纯 CPU |
|---|---|---|---|---|
| **普通路径** | 未勾选任何 ⚠ 组（中/英/日/拉丁/希腊文等） | ≥12GB → **PP-OCRv6 CUDA**；≤8GB → **ncnn Vulkan** | **ncnn Vulkan** | **ncnn Vulkan**（模式切 **CPU**） |
| **⚠ 专用路径** | 勾选了任一 ⚠ 组 | **PP-OCRv6 引擎**（自动回退 v5 分语种模型，~3 秒/页） | **PP-OCRv5 (Paddle CPU) 备选** | 同左 |

- **普通路径为什么 ≤8GB 走 Vulkan**：Vulkan 显存占用低、可开双实例，批处理速度更快（约 2.2 页/秒，CUDA 约 1.1 页/秒）；大显存卡才用 CUDA 换最高精度
- **⚠ 路径为什么 N 卡都走 v6**：这些文字不在 v6/ncnn 通用字典（实测 0 字符覆盖），而 PP-OCRv5 分语种模型只有 v6 引擎能调；显存大小不影响可用性
- **v5 分语种模型目前走 CPU 推理**（ONNX Runtime 的 CUDA 内核对部分张量形状会报 Conv 运行期异常，与显存大小无关），所以 ⚠ 语言识别速度与显卡档次无关（约 3 秒/页）；"NVIDIA → v6 引擎"只表示选用哪个引擎，不代表独占 GPU 加速
- 配置摘要栏会明示"已切换：勾选⚠语言 → PP-OCRv6 引擎自动回退分语种模型 / PP-OCRv5 (Paddle CPU) 备选引擎"

**其余参数**由"文档类型 + 精度档 + 显存档"决定（与引擎选择相互独立）：

文档类型只决定 **竖排检测 / 方向纠正**：

| 文档类型 | 竖排检测 | 方向纠正 |
|---|---|---|
| 普通文档 | 关 | 关 |
| 古籍竖排 | **开** | 关 |
| 扫描件/照片 | 关 | **开** |

边长与渲染倍率改由「精度档 + 显存档」统一决定：

| 速度档 / 显存档 | 图像边长 | 渲染倍率 |
|---|---|---|
| 速度优先 | **2240**（一律） | **2x** |
| 标准平衡 | **2240**（一律） | **2x** |
| 精度优先 · 大显存（≥12GB / 纯CPU） | **2560** | 古籍 → **3x**；其余 → 2x |
| 精度优先 · 小显存（≤8GB） | **2240** | **2x** |

精度档只决定模型 / 浮点精度 / 对齐：

| 精度档 | 模型 | 批处理数 | 浮点精度 | 对齐(shrink) |
|---|---|---|---|---|
| 速度优先 | v6 small | **16** | FP16 | 关 |
| 标准平衡 | v6 medium | **16** | FP32 | 关 |
| 精度优先 | v6 medium | **16** | FP32 | **开** |

> **渲染 3x 的唯一触发条件**：古籍竖排 + 精度优先 + 大显存（或纯CPU）。其余情况一律 2x。
> **批处理数与精度档无关**，三档统一 **16**。
> **双实例**：除纯 CPU 档外默认开启；纯 CPU 档自动关闭（无增益）。
> 渲染倍率下拉文案 `2x` 改为 **`2x（高清）`**。

### 2d. 专业模式：引擎列表与语言下拉修正（本轮）

按实测字典逐字符核对后，修正了专业模式里三处"选了也会乱码 / 自相矛盾"的地方：

**① ncnn Vulkan 的语言下拉不再列出它认不了的文字**

之前 ncnn（Vulkan / CPU）的语言下拉里还能看到**西里尔字母、韩文、阿拉伯文、天城文、泰文**等选项 —— 这些文字在 ncnn 的 v6 字典里是 **0 字符覆盖**，选了必然输出乱码/空结果，与"下拉里能选"自相矛盾。
现按实测覆盖过滤语种列表，**不再列出**这 32 项：

| 文字系 | 代码 | 数量 |
|---|---|---|
| 韩文 | `korean` | 1 |
| 西里尔文系 | ru / uk / be / bg / mk / mn / kk / ky / tg / tt / ba / cv / rs_cyrillic | 13 |
| 阿拉伯字母系 | ar / fa / ug / ur / ps / sd / ks / bal | 8 |
| 天城文系 | hi / mr / ne / sa / bh / mai / kok | 7 |
| 泰 / 泰卢固 / 泰米尔 | th / te / ta | 3 |

- **希腊文保留**：实测 v6 字典含 **76 个希腊字符**，识别正确，不是 ⚠ 语言。
- **多语言混排保留**：`中·英·日 + 拉丁语系` 与 `46 种拉丁语系` 都在 v6 字典覆盖内。
- 过滤用的集合与「开跑守卫」**共用同一份**（`_NCNN_UNSUPPORTED`），避免"下拉能选、守卫又拦"。

**② PP-OCRv5 (Paddle CPU) 的模型下拉不再写"中文"**

该引擎的模型由**语言**决定（服务端按语言路由到 11 套官方分语种模型），下拉里却写着"中文 (默认)"，容易误解。
现改为 **「按语言自动选择 (官方分语种模型)」并置灰**（单模型的 PP-OCRv3 同样置灰）。

**③ 「PP-OCR (ncnn CPU)」合并进 ncnn Vulkan 的 CPU 模式**

实测 `PPOCR-ncnn-CPU/ppocr_ocr_cpu.exe` 与 `PPOCR-ncnn-Vulkan/ppocr_ocr_vulkan.exe` 的 **MD5 完全相同**（`c9e7532ab90ec403acddb1fd5cb8d359`）—— 本就是**同一份二进制**。
因此引擎下拉**不再单独列出**「PP-OCR (ncnn CPU)」（共 5 项），纯 CPU 运行统一由 **ncnn Vulkan 的「CPU模式」**（`use_vulkan=false`）承担：

- 简单模式里"核显 / 纯CPU"档现在选 **ncnn Vulkan + CPU模式**，行为与原来完全一致
- 旧配置若存的是 `ncnn_cpu`，启动时自动映射到 `ncnn_vulkan`
- 「引擎 ↔ 模式」的强制联动已移除：`ncnn Vulkan + CPU模式` 现在是合法状态，不会再被改回 GPU

**④ 新增「引擎 ↔ 语言 不匹配」提示与一键跳转**

- **切换引擎时**：新引擎不支持当前语言 → 弹窗「是否切换到支持该语言的 <推荐引擎>？」
- **点「开始处理」时**：守卫弹窗按钮改为「**切换到推荐引擎** / 仍用当前引擎 / 取消」
- 推荐规则与简单模式一致：NVIDIA 机器 → **PP-OCRv6 ONNX CUDA**（⚠ 语言自动回退 v5 分语种模型）；否则 → **PP-OCRv5 (Paddle CPU)**

# CathayOCR Pro v1.2.4 更新说明（历史）

> 发布日期：2026-09-11

---

## 🎯 本次更新（修复除 Vulkan 外其他引擎全部不可用）

### 问题现象

选择 **ncnn Vulkan 以外**的引擎（PP-OCRv6 ONNX / PP-OCRv5 / 经典版 / ncnn CPU / EasyOCR）时：引擎能正常启动，界面不报错，但处理完成后

- `_result.txt` 里**只有文件头**（源文件 / 总页数 / 渲染倍数 / 提取时间），**正文 0 字**
- 导出的 `_layered.pdf` **没有任何文字层**，无法搜索
- 只有 **ncnn Vulkan** 引擎一切正常

### 根本原因

`PDFProcessor.ocr_consumer()`（OCR 消费线程）在每页识别的第一步执行：

```
timeout_sec = self.ocr._instances[0].get_dynamic_timeout()
```

但 `get_dynamic_timeout()` **只定义在 `NcnnVulkanAdapter` 里**，基类 `OCREngineAdapter`、`PaddlePipeAdapter`、`NcnnCPUAdapter` 均没有该方法。因此选用非 Vulkan 引擎时，这一行立即抛出：

```
AttributeError: 'PaddlePipeAdapter' object has no attribute 'get_dynamic_timeout'
```

该调用**位于 try 之外**，OCR 消费线程当场死亡 → 该线程负责的页面永远不会被识别 → 导出结果为空、PDF 无文字层。

### 问题来源

**不是 v1.2.3 引入的**。v1.1.3 加入看门狗与动态超时时只围绕 Vulkan 引擎实现，`get_dynamic_timeout()` 与 `restart()` 都只写在 `NcnnVulkanAdapter` 上；v1.2.3 的改动未触及这里。因此在 v1.2.4 之前，**除 Vulkan 外的引擎实际上一直不可用**（引擎能启动，一处理页面线程即崩）。

### 修复方案

1. **动态超时提升到基类**：`get_dynamic_timeout()` 在基类 `OCREngineAdapter` 提供通用默认实现——聚合所有活跃引擎实例的耗时样本，样本不足 3 个返回 180 秒，否则按 p90×3 升档、上限 300 秒。`NcnnVulkanAdapter` 保留自身实现，**Vulkan 行为零变化**。
2. **耗时记录下沉**：基类 `__init__` 新增 `_ocr_times`，`PaddlePipeAdapter`、`NcnnCPUAdapter` 在每页识别后记录耗时 → **「慢设备自动升档超时」对所有引擎生效**（原来只对 Vulkan 生效）。
3. **恢复能力补齐**：基类补充默认 `restart()`（stop + start），看门狗对非 Vulkan 引擎的自动恢复不再静默失效（原调用点有 try/except，属于「不报错但不工作」）。
4. **调用处加兜底**：`ocr_consumer` 取动态超时时用 `getattr` 判断可调用性，避免同类崩溃再次发生。

### 验证结果（真实 PDF 端到端）

| 引擎 | 修复前 | 修复后 |
|------|--------|--------|
| PP-OCRv6 (ONNX CUDA) | 0 字 + 线程崩溃 | 42 字 OK |
| PP-OCRv5 (Paddle CPU) | 0 字 + 线程崩溃 | 42 字 OK |
| 经典版 (win7_classic) | 0 字 + 线程崩溃 | 41 字 OK |
| ncnn CPU | 0 字 + 线程崩溃 | 42 字 OK |
| EasyOCR（拉丁语系） | 0 字 + 线程崩溃 | 88 字 OK |
| ncnn Vulkan | 正常 | 正常（逻辑未改动） |

# CathayOCR Pro v1.2.3 更新说明（历史）

> 发布日期：2026-08-27

---

## 🎯 更新内容（同步 Lite v1.2.3）

### 1. 修复「竖排识别」无效的 Bug（重要）

**问题现象**：勾选「竖排文字」后，竖排古籍的 OCR 结果顺序依然混乱，无法直接阅读。

**排查结果**：该选项实际上是一个**无效开关**——勾选状态虽然会沿「界面 → 工作线程 → OCR 客户端 → 引擎参数构建」完整链路传递，但最终写入引擎配置时**从未被使用**，引擎始终按默认横排顺序输出结果。

**修复方案**：勾选「竖排识别」后，在导出结果前按竖排阅读顺序重新排列识别文本——**先按中心点 X 降序（右→左），再按 Y 升序（上→下）**。纯 CPU 后处理，单页耗时 <10ms。

**改动明细**：
- 界面选项「竖排文字」更名为「**竖排识别**」，默认**不勾选**（保持与旧版行为一致）
- 新增排序逻辑：按检测框中心点 X 降序（右→左）、Y 升序（上→下）重排
- 排序在导出层完成，不污染原始识别结果

### 2. 修复竖排文字写不进 PDF / 搜索不到的问题（重要）

**问题现象**：竖排古籍处理完后，`_result.txt` 里文字完整，但导出的双层 PDF 里搜不到、甚至缺字。

**排查结果**：竖排古籍的 OCR 检测框是「高>宽」的竖条框，但导出时文字仍按**横排**（rotate=0）写入 PDF。整句文字横向展开后超出页面右边界，超出页面的文字被 PDF 查看器/提取器**裁剪丢弃** → PDF 搜不到、缺字。

**修复方案**：`write_results` 写入时判断检测框形态：
- **竖条框（原始高>宽）** → 文字以 **rotate=270 从框顶向下竖排写入**，整句完整落在页面内，可正常搜索
- **横条框（宽>高）** → 保持原有横排逻辑，不受影响

**使用注意**：竖排写入与「竖排识别」选项**联动**——必须勾选「竖排识别」才按竖排方式写入；不勾选保持旧版横排行为。

### 3. 修复 OCR 坐标超界 Bug（文字落页面外）

**问题现象**：OCR 引擎处理的是 scale=2 渲染图像，返回的检测框为像素坐标，但写入 PDF 时未除以 scale 直接使用 → 大量文字落在页面外，无法提取/搜索。

**修复方案**：写入 PDF 前将坐标 `x0/=scale; y0/=scale; x2/=scale; y2/=scale`，scale=1 时与旧版完全一致。

### 4. 新增「覆盖旧OCR」功能（替换双层文本）

**功能说明**：勾选「覆盖旧OCR」后，导出双层 PDF 时**物理删除原 PDF 中的全部旧文字层**，仅叠加本次新识别出的文字层。

**技术要点**（PyMuPDF 修订 Redaction 方案）：
- 对每页标记整页修订 → 应用修订时**保留图像层**（`PDF_REDACT_IMAGE_NONE`）与**矢量图形**（`PDF_REDACT_LINE_ART_NONE`）
- 扫描图像 300% 缩放依然无损；矢量图形完整保留
- 新文字层以隐形可搜索方式写入，Ctrl+F 可正常搜索
- 未勾选时完全跳过清除步骤，维持原有「新旧文字层并存」逻辑，向后兼容
