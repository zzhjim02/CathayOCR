# CathayOCR Pro v1.2.4 更新说明

> 发布日期：2026-09-11

---

## 🎯 本次更新（修复除 Vulkan 外其他引擎全部不可用）

### 问题现象

选择 **ncnn Vulkan 以外**的引擎（PP-OCRv6 ONNX / PP-OCRv5 / 经典版 / ncnn CPU / EasyOCR）时：引擎能正常启动，界面不报错，但处理完成后

- `_result.txt` 里**只有文件头**（源文件 / 总页数 / 渲染倍数 / 提取时间），**正文 0 字**
- 导出的 `_layered.pdf` **没有任何文字层**，无法搜索
- 只有 **ncnn Vulkan** 引擎一切正常

### 根本原因

`PDFProcessor.ocr_consumer()`（OCR 消费线程）在每页识别的第一步执行：

```
timeout_sec = self.ocr._instances[0].get_dynamic_timeout()
```

但 `get_dynamic_timeout()` **只定义在 `NcnnVulkanAdapter` 里**，基类 `OCREngineAdapter`、`PaddlePipeAdapter`、`NcnnCPUAdapter` 均没有该方法。因此选用非 Vulkan 引擎时，这一行立即抛出：

```
AttributeError: 'PaddlePipeAdapter' object has no attribute 'get_dynamic_timeout'
```

该调用**位于 try 之外**，OCR 消费线程当场死亡 → 该线程负责的页面永远不会被识别 → 导出结果为空、PDF 无文字层。

### 问题来源

**不是 v1.2.3 引入的**。v1.1.3 加入看门狗与动态超时时只围绕 Vulkan 引擎实现，`get_dynamic_timeout()` 与 `restart()` 都只写在 `NcnnVulkanAdapter` 上；v1.2.3 的改动未触及这里。因此在 v1.2.4 之前，**除 Vulkan 外的引擎实际上一直不可用**（引擎能启动，一处理页面线程即崩）。

### 修复方案

1. **动态超时提升到基类**：`get_dynamic_timeout()` 在基类 `OCREngineAdapter` 提供通用默认实现——聚合所有活跃引擎实例的耗时样本，样本不足 3 个返回 180 秒，否则按 p90×3 升档、上限 300 秒。`NcnnVulkanAdapter` 保留自身实现，**Vulkan 行为零变化**。
2. **耗时记录下沉**：基类 `__init__` 新增 `_ocr_times`，`PaddlePipeAdapter`、`NcnnCPUAdapter` 在每页识别后记录耗时 → **「慢设备自动升档超时」对所有引擎生效**（原来只对 Vulkan 生效）。
3. **恢复能力补齐**：基类补充默认 `restart()`（stop + start），看门狗对非 Vulkan 引擎的自动恢复不再静默失效（原调用点有 try/except，属于「不报错但不工作」）。
4. **调用处加兜底**：`ocr_consumer` 取动态超时时用 `getattr` 判断可调用性，避免同类崩溃再次发生。

### 验证结果（真实 PDF 端到端）

| 引擎 | 修复前 | 修复后 |
|------|--------|--------|
| PP-OCRv6 (ONNX CUDA) | 0 字 + 线程崩溃 | 42 字 OK |
| PP-OCRv5 (Paddle CPU) | 0 字 + 线程崩溃 | 42 字 OK |
| 经典版 (win7_classic) | 0 字 + 线程崩溃 | 41 字 OK |
| ncnn CPU | 0 字 + 线程崩溃 | 42 字 OK |
| EasyOCR（拉丁语系） | 0 字 + 线程崩溃 | 88 字 OK |
| ncnn Vulkan | 正常 | 正常（逻辑未改动） |

# CathayOCR Pro v1.2.3 更新说明（历史）

> 发布日期：2026-08-27

---

## 🎯 更新内容（同步 Lite v1.2.3）

### 1. 修复「竖排识别」无效的 Bug（重要）

**问题现象**：勾选「竖排文字」后，竖排古籍的 OCR 结果顺序依然混乱，无法直接阅读。

**排查结果**：该选项实际上是一个**无效开关**——勾选状态虽然会沿「界面 → 工作线程 → OCR 客户端 → 引擎参数构建」完整链路传递，但最终写入引擎配置时**从未被使用**，引擎始终按默认横排顺序输出结果。

**修复方案**：勾选「竖排识别」后，在导出结果前按竖排阅读顺序重新排列识别文本——**先按中心点 X 降序（右→左），再按 Y 升序（上→下）**。纯 CPU 后处理，单页耗时 <10ms。

**改动明细**：
- 界面选项「竖排文字」更名为「**竖排识别**」，默认**不勾选**（保持与旧版行为一致）
- 新增排序逻辑：按检测框中心点 X 降序（右→左）、Y 升序（上→下）重排
- 排序在导出层完成，不污染原始识别结果

### 2. 修复竖排文字写不进 PDF / 搜索不到的问题（重要）

**问题现象**：竖排古籍处理完后，`_result.txt` 里文字完整，但导出的双层 PDF 里搜不到、甚至缺字。

**排查结果**：竖排古籍的 OCR 检测框是「高>宽」的竖条框，但导出时文字仍按**横排**（rotate=0）写入 PDF。整句文字横向展开后超出页面右边界，超出页面的文字被 PDF 查看器/提取器**裁剪丢弃** → PDF 搜不到、缺字。

**修复方案**：`write_results` 写入时判断检测框形态：
- **竖条框（原始高>宽）** → 文字以 **rotate=270 从框顶向下竖排写入**，整句完整落在页面内，可正常搜索
- **横条框（宽>高）** → 保持原有横排逻辑，不受影响

**使用注意**：竖排写入与「竖排识别」选项**联动**——必须勾选「竖排识别」才按竖排方式写入；不勾选保持旧版横排行为。

### 3. 修复 OCR 坐标超界 Bug（文字落页面外）

**问题现象**：OCR 引擎处理的是 scale=2 渲染图像，返回的检测框为像素坐标，但写入 PDF 时未除以 scale 直接使用 → 大量文字落在页面外，无法提取/搜索。

**修复方案**：写入 PDF 前将坐标 `x0/=scale; y0/=scale; x2/=scale; y2/=scale`，scale=1 时与旧版完全一致。

### 4. 新增「覆盖旧OCR」功能（替换双层文本）

**功能说明**：勾选「覆盖旧OCR」后，导出双层 PDF 时**物理删除原 PDF 中的全部旧文字层**，仅叠加本次新识别出的文字层。

**技术要点**（PyMuPDF 修订 Redaction 方案）：
- 对每页标记整页修订 → 应用修订时**保留图像层**（`PDF_REDACT_IMAGE_NONE`）与**矢量图形**（`PDF_REDACT_LINE_ART_NONE`）
- 扫描图像 300% 缩放依然无损；矢量图形完整保留
- 新文字层以隐形可搜索方式写入，Ctrl+F 可正常搜索
- 未勾选时完全跳过清除步骤，维持原有「新旧文字层并存」逻辑，向后兼容

# CathayOCR Pro v1.1.3 更新说明（历史）

> 发布日期：2026-08-02

## 优化改动

| 改动 | 原值 | 新值 | 影响 |
|------|------|------|------|
| 看门狗超时地板值 | 300s | 180s | 设备正常时与原始版本一致，超时更快回退，不卡住 |
| 慢设备自动升档 | 无 | p90×3 > 180s 时升到 300s | 慢设备不会被误判为超时 |

### 改动说明

**看门狗超时策略优化**（`get_dynamic_timeout`）：

- **默认超时 180s**：与原始超时一致，引擎卡死时更快 timeout 触发看门狗恢复，不再额外多等 120s
- **慢设备自动升档**：如果检测到本地处理速度慢（前几页的 p90×3 > 180s），自动升到 min(p90×3, 300s)，避免慢设备上的正常页面被误判为超时
