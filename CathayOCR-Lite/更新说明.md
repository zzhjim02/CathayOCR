## 起点：v1.2.4（基线）

v1.2.4 是长期稳定运行的版本，也是整个 v1.3.x 的**引擎链路基线**。
它的引擎调用方式、看门狗、双实例并行、超时策略、临时文件、请求派发、结果写入顺序，
在此后的 v1.3.x 中**一直被刻意保持原样**——凡是「改动引擎运行时行为」的方案一律不采用。

> 之所以如此：你的实际诉求是「不要动我跑得稳的东西」。因此 v1.3.x 的定位始终是
> **在 v1.2.4 这条引擎链路之上，只补那些与「引擎怎么跑」无关的东西**。

## v1.3.0 —— 内部试验稿（未对外发布，仅作技术验证）

这一版做了大量工作，是后面所有成果的来源：

- **新增「瘦启动器 + 独立运行日志窗口」**：双击 `CathayOCR Lite.exe` 即启动，无黑框；日志窗口实时显示 GPU 检测 / 引擎日志 / 报错堆栈（用软件自带的 `portapython\python.exe` 运行原主程序源码，不打包主程序）。
- **三类稳定性修复**：
  1. 退出时不再 `taskkill /f /im` **按进程名全系统强杀**，改为枚举进程按完整路径、**只结束本软件目录内**的同名进程（否则会误杀另一个副本 / 另一份安装正在跑的引擎）；
  2. 不再用 `os.dup2` 全局重定向 stderr，改用 MuPDF 官方开关 `fitz.TOOLS.mupdf_display_errors(False)`；
  3. 关窗口时若引擎实例不存在，不再多启动 2 个引擎进程再关掉。
- **语言 / 字典路由修复**、**出错保护层**（完整性闸门 + 三级恢复）、**界面增强**（迷你窗口、列表管理、输出目录说明等）——这些在 v1.3.1 中正式定型。

> ⚠ **但 v1.3.0 在实际运行中暴露了「空白文件」问题**：GPU 长时间满负载被 Windows 的
> **TDR 超时机制**打断后，引擎进程还活着、端口还在、还照常回话，**只是每页都算不出来**，
> 把每一页都报成「无文字」；程序把这些页当正常空白放行 → 输出一批**空白壳**。
>
> 正因如此，v1.3.0 **只作内部试验稿**（对外备份标注「有 BUG」）。v1.3.1 改为
> **以 v1.2.4 引擎链路为基线重做**，把 v1.3.0 那批与「引擎运行行为」无关的成果移植过来。

## v1.3.1 —— 以 v1.2.4 引擎链路为基线重做（正式起点）

> **本版定位**：引擎调用方式、看门狗、双实例并行、超时策略、临时文件、请求派发、
> 结果写入顺序，**全部保持 v1.2.4 原样**。在此基础上只补三类与「引擎运行时行为」无关的东西：
> ① 语言与字典路由修复；② 出错保护层；③ 界面与可维护性增强。
>
> 一句话：**引擎怎么跑，和 v1.2.4 一模一样；变的是——语言终于选对了、出错时看得见、界面更好用了。**

### 1. 修复「模型 ↔ 字典错配」Bug（重要）

**现象**：专业模式选 `v4 Mobile` 或 `v6 Tiny` 模型后，识别结果可能整页乱码，或引擎算到一半卡死、触发超时。

**根因**：旧代码按**模型名字符串猜**字典（`if "v3" in ... elif "v6" in ... else ...`），于是两个模型被分错字典：

| 模型 | 模型实际输出类别数 | 应配字典（行数） | 旧版实际选中 | 结果 |
|---|---|---|---|---|
| `PP_OCRv4_mobile` | 6625 | `ppocr_keys_v1.txt`（6624） | `ppocr_keys_v5.txt`（18384） | ❌ 错配 11759 行 |
| `PP_OCRv6_tiny` | 6906 | `ppocr_keys_v6_tiny.txt`（6905） | `ppocr_keys_v6.txt`（18709） | ❌ 错配 11803 行 |

**为什么危险**：识别模型的输出类别数必须与字典行数严格一致（类别数 = 字典行数 + 1 个 CTC 空白符）。
错配一万多行时解码索引对不上——轻则乱码，重则引擎异常、请求超时。

**修复**：改为**按实际选中的模型**路由字典，且 `v6_tiny` 必须先于 `v6` 判断：

```python
def _ncnn_keys_file_for_model(model_base):
    m = model_base or ""
    if "v6_tiny" in m:         return "ppocr_keys_v6_tiny.txt"
    if "v3" in m or "v4" in m: return "ppocr_keys_v1.txt"
    if "v6" in m:              return "ppocr_keys_v6.txt"
    return "ppocr_keys_v5.txt"
```

**附带修好**：`ppocr_keys_v6_tiny.txt` 这份字典在旧版中**从未被任何模型选中过**。

### 2. 语言下拉大扩充，并按「当前字典的真实能力」如实标注

轻量版 7 个模型共用 **4 份字典**（v1 / v5 / v6 / v6_tiny），对各文字系的覆盖差别很大
（如日文假名在 v1 字典里只有约 4%，外语字母在 v6_tiny 里为 0）。旧版把语言一股脑全列出来、不作区分，用户选了跑不动也无提示。

本次改动：

- **简单模式**语言项：6 → **14 项**（含一条「以下文字需专业版」分隔行）
- **专业模式**语言项：15 → **19 项**（含一条说明行 + 一条分隔行）
- 下拉中**灰色不可选**的条目 = 当前 Lite 的 ncnn 字典确实不覆盖该文字系：
  韩文（谚文）、俄文等西里尔文系、阿拉伯文系、天城文系（印地/马拉地等）、泰文、泰卢固文、泰米尔文
- 越南文标注「**部分支持·可能缺重音**」
- 语言列表**随所选模型动态刷新**——切换模型 → 所用字典变了 → 语言可选项与灰显状态同步更新

### 3. 修复三处「选了语言却不生效 / 悄悄跑错语言」

1. **语言表如实标注**各语言在轻量版的支持状态（旧版把不支持的也一并列出、无任何提示）
2. **字典跟随实际选中模型**（见第 1 条）
3. **简单模式 ↔ 专业模式的语言同步改为按「语言代码」匹配**
   - 旧版按**显示文本**匹配（`findText`）：一旦两边文案不同（如专业模式「Ελληνικά (希腊文)」对不上简单模式「希腊文」），就**匹配失败、默默回退到第 0 项用中文跑**，用户完全看不出来
   - 现在按语言代码同步，不会再悄悄跑错语言

### 4. 出错保护层：完整性闸门 + 三级恢复（**宁可重跑，也绝不悄悄少页**）

**背景**：旧版 `write_results` 里有一句 `if result.get("code") != 100: continue` —— 识别失败的页会被**无声丢掉**，你拿到的可能是一份**少了几页却看不出来**的结果。失败有两条来源：

1. 引擎重启时，另一个线程正在等待的请求被 socket 断开打断，该页以错误码落入结果集；
2. 页面渲染线程异常时**只打印一行日志就直接跳过**，该页永远不会进入识别队列。

**修复**（都在 `PDFProcessor` 里）：

| 机制 | 作用 |
|---|---|
| `_RESULT_OK_CODES = (100, 101)` + `_incomplete_pages()` | 把「引擎明确回复本页无文字」（`101`）算作**有结论**；只有真正失败的页才判为不完整 |
| 三级恢复 | 某页失败 → **重试该页 1 次**（若是超时，先把两个引擎一起重启）→ 仍失败 → **整份文件重处理 1 次** → 仍失败 → 跳过该文件，并在**源文件所在目录写 `{文件名}_OCR未完成警告.txt`**，同时抛出错误（不再伪装成「已取消」） |
| 「取消 ≠ 完成」 | 用户主动取消时提示「已取消」，不再误报「批量处理完成」 |

**铁律**：**宁可整份文件重跑 / 直接报错，也绝不产出一份少了几页却看不出来的结果。**

> 提醒：`101` 必须算「有结论」——否则带空白页的正常文件会被无限重跑。

## v1.3.2 —— 引擎层 3 处修复（界面一行未动）

现场日志（2026-10-10，第 134 / 136 / 139 册）显示：每一次「卡住」都是同一条链 ——
**某页整整 180 秒没有响应** → 看门狗判定「引擎假死」→ 重启两个引擎 → 速度从 1.0 页/秒掉到 0.2 页/秒再慢慢爬回来。逐条对照代码，定位到 3 个成因。

### 1. 「孤儿引擎」——最主要的成因

`_ensure_running()` 原本是**「1 秒探活失败 → 直接再启动一个引擎进程」**。探活超时只有 1 秒，引擎忙时**必然失败**；而此时旧进程还在跑，重新启动会把旧进程引用覆盖掉——旧进程从此没人管，变成**霸占端口的孤儿**。日志里能看到同一端口被**连续启动两次**。之后请求随机打进孤儿：`connect` 成功、回复永远等不到 → `recv` 挂满 180 秒 → 看门狗重启 → 又生孤儿 = **周期性卡顿**。

**改法**：`_ensure_running()` 改成**只检查、绝不起进程**：

1. 自己的引擎进程句柄还活着 → 直接放行（1 秒探活失败只代表「忙」，不能据此判死）；
2. 进程不在、但端口有人响应 → 那是不属于我们的占位者（孤儿 / 别处的同类程序）→ 清掉它；
3. 进程真死了 → 只清掉悬空引用，**不在这里重启**（重建统一交给看门狗，两个引擎一起重启）。

### 2. 「引擎不可用」与「真超时」分不开

引擎不可用时返回 `code=102, data="...timeout..."` —— 靠硬塞 `timeout` 关键字去蹭看门狗那条判定。代价是两者永远分不开（日志出现「超时 1s (limit=180s)」这种自相矛盾的记录）；而消费端本来就是按 `103` 写的恢复分支，**那条路从来没走到过**。

**改法**：引擎不可用改为返回 `103`（与消费端语义对齐）；`102` 只留给真超时与 TCP 错误。

### 3. 「并发重启抢同一端口」

两个 consumer 常常同时判定超时、同时调 `restart_all()` → 同一端口被连续启动两次（第二次 `bind` 不上，反倒留下新占位者）。

**改法**：`restart()` 用**进程启停专用锁** `_proc_lock` 串行化，并加 **8 秒抑制窗**（本端口刚重启过、且新引擎确实活着 → 跳过这次重复重启）。该锁与 `self.lock` **分开**：后者会被卡在 `recv` 的线程持满 180 秒，绝不能复用。

### 明确**没有**改的东西

- **界面全部**（按钮、迷你窗口、语言下拉、列表管理、日志窗口入口、图标）—— 一行未动
- **完整性闸门 + 三级恢复**（`MAX_PAGE_RETRY=1` / `MAX_FILE_RETRY=1` / 失败写警告文件）—— 一行未动
- **双实例轮询分页、动态超时**（floor 180 / ceiling 300）、**分页写回顺序** —— 一行未动
- `self.lock` 仍照 v1.2.4 包住整段请求；`103` / `_TCP_TX_RETRY` 等既有取舍保持原状

### 影响面（AST 逐符号核对）

| 项目 | 结果 |
|---|---|
| 新增方法 | `NcnnVulkanAdapter._engine_is_ours()` —— **1 个** |
| 修改方法 | `NcnnVulkanAdapter.__init__ / _tcp_request / _ensure_running / restart` —— **4 个** |
| 附带修改 | `MainWindow.__init__` —— 仅窗口标题版本号 |
| 删除符号 | **0 个** |

行为自检（用假进程对象，**不启动引擎、不碰显卡**）：T1 引擎忙但进程活着 → 返回 True 且不起进程；T2 端口被占位者霸住 → 清理孤儿；T3 进程真死 → 清空引用、不起进程；T4 8 秒抑制窗生效；T5 引擎不可用 → 约 0 秒返回 `103`。**全部通过。**

## v1.3.3 —— 并发竞态修复 + 日志语气分级

### 一、修复：临时图片「边写边读」竞态

**现象**：长时间批量识别时，日志间歇出现「某页连接被重置」（WinError 10053 / 10054），程序自动取回后继续。

**根因（两处叠加）**：

1. **轮询取号没有加锁**：`OCRClient.ocr_image_base64()` 里
   `idx = self._adapter_index % len(self._instances); self._adapter_index += 1`
   两个识别线程并发执行时可能**同时读到同一个值** → 双双选中**同一个引擎实例**。
2. **写临时图片在锁外**：`NcnnVulkanAdapter.run_base64()` 里图片写进**该实例复用的同一个临时文件**，但写文件这一步在 `self.lock` 之外；两个线程撞上同一实例时，一个线程会在**引擎正读取该 png 的同时覆写它** → 引擎读到半张图 → 连接被打断。

**修法**：

- `ocr_image_base64()`：取号与自增放进同一把锁（新增 `self._pick_lock`）。
- `run_base64()`：「写临时图 + 发请求」整段纳入 `self.lock`；锁类型由 `Lock` 改为 **`RLock`**（`_tcp_request` 内部也会取这把锁，普通 `Lock` 同线程二次获取会死锁）。

**影响面**：新增函数 0 个、删除函数 0 个；改动 `NcnnVulkanAdapter.__init__` / `run_base64` / `OCRClient.ocr_image_base64` / `PDFProcessor.ocr_consumer`。引擎启停语义、双实例轮询策略、动态超时、完整性闸门、三级恢复、迷你窗口、界面 —— **未改动**。

### 二、日志语气分级

按「**要不要用户操心**」分两档：

| 情况 | 语气 | 说明 |
|---|---|---|
| 单页连接瞬时中断（10053/10054，引擎进程正常） | **平实一句** | 程序自动取回，**无需用户做任何事** |
| 整页自动重试 | **不再单独刷一行** | 全自动，无需介入 |
| 真超时 / 引擎不可用 / 需要全文件重跑 / 跳过文件 | **保留告警语气** | 这些确实需要留意 |

要点：平实文案里**刻意不含** `error / 错误 / 失败 / 超时 / 重试 / 重启` 等会被日志窗口标红的关键字。

## v1.3.4 —— 空白根源治理

**v1.3.4 = v1.3.3 + 引擎日志落盘 + 空白页引擎核验（探针）+ 日志语气平实化 + 两处追加收敛。**

### 1. 引擎「活着但已经废了」的怪病（空白文件的根源）

**铁证**（引擎自己的日志 + Windows 系统日志）：

- 引擎日志里 `vkQueueSubmit failed -4` 出现 **6173 次**（-4 = `VK_ERROR_DEVICE_LOST`）；
- 系统日志在故障时刻密集出现 `nvlddmkm ID=153`（显示驱动停止响应并已恢复）。

**机制**：Windows 的 TDR 机制默认给 GPU 命令 **2 秒**限时，超时就强制重置显卡驱动。驱动被重置后，Vulkan 设备按规范**永久死亡**——但 ncnn 引擎不退出也不重建，于是进程活着、端口在、还照常回话，**只是每次计算都失败**，把每一页都报成「无文字」(101)。程序把这些页当正常空白放行 → 产出大量空白壳。

### 2. 两个配套修复（必须一起上才有效）

| 改动 | 作用 |
|---|---|
| **引擎日志落盘** | 原来引擎报错写进一根「没人读的管道」，写满约 4KB 就把引擎憋死（表现为突然不响应），且崩溃原因全部丢失。现在落到 `ncnn\PPOCR-ncnn-Vulkan\engine_<端口>_stderr.log`，既不憋死、事后也能翻到引擎自己的原话。 |
| **空白页引擎核验** | 引擎日志不憋死后，废引擎会一直接单一直失败。所以加了核验：只在引擎报「无文字」时，拿一张它必然认得出的白底黑字图（「OCR TEST 12345」）问它一次，**连续两次认不出 = 引擎已废** → 自动重建引擎 + 重跑本页。正常书没有空白页，一次探针都不会发。 |

### 3. 日志语气平实化

恢复类日志（重建引擎、重跑本页、整份文件重跑）改成平实的 `[自动恢复]` 语气，不再红/橙刷屏。**只有一种情况保留红色告警：整份文件重跑用尽、被跳过并生成警告文件** —— 那才是真的需要你处理。

### 4. 「连接瞬时中断」不再逐页刷屏

主程序和引擎之间是**本机 TCP 通信**（127.0.0.1），每识别一页开一条连接。偶尔某条连接会被引擎 TCP 服务端重置一次（10053 / 10054），程序**立刻重发同一页**就取回了——这是**良性的连接级抖动**：引擎进程全程活着、与 GPU/驱动无关，代价只是一次本地重发（毫秒级）。

以前每抖一次刷一行，一册 700 页能刷几十行，容易被误读成故障。现在改为 **处理完一本书只汇总一行**：

```
[自动恢复] 本册共 23 页连接瞬时中断，均已自动取回（不影响结果）
```

有才打、没有不打；一页都没抖就完全不出这行。汇总行同时进入运行日志窗口和 `logs\` 自动日志。

### 5. 性能收敛：去掉 base64 中转（每页省一次编解码）

渲染线程把书页编成 PNG 后，原来要先 `base64` 编码放进队列，消费线程再解码回字节写临时图——**一来一回纯属多余**（引擎最终要的是磁盘上那张图，base64 根本不参与传输）。

现在队列里直接放 **PNG 原始字节**，两端都不再编解码：

- 每页省 **一次编码 + 一次解码**（约 17ms + 9ms）；
- 队列里的「在飞图片」内存从约 **10.2MB/页降到 7.7MB/页**（base64 会把体积撑大 33%）；
- **不改任何字节内容、不改识别结果**：base64 往返无损可逆，新旧两条路交给引擎的字节**逐字节相同**（已用等价性单测验证通过）。

### 改动清单（AST 级核对）

- **新增 8 个函数**：`_open/_close/_note/_read_stderr_log`（日志落盘 ×4）、`_get_probe_image_b64`、`_probe_extract_text`、`_probe_instance`、`_walk`（探针 ×4）
- **修改 6 个方法**：`__init__`（探针锁）、`_start_gpu`/`start`（日志落盘）、`ocr_image_base64`（101 时核验）、`ocr_consumer`/`process_pdf`（日志平实化）、`stop`（关句柄）
- **删除 0 个**；不碰看门狗语义、结果码定义、完整性闸门、动态超时、写回顺序、任何界面
- **日志收敛**：`process_pdf` 内新增本册计数器 `_tcp_jitter`，把逐页刷屏的「第 N 页连接瞬时中断」收成每册一行。**纯日志行为，不改判定逻辑**
- **去 base64**：新增模块级 `_img_to_bytes()`；渲染入队改传 `png_bytes`、消费端改名 `img_data`；`run_base64` 内 `b64decode(...)` → `_img_to_bytes(...)`。**纯数据管道改动，不改判定逻辑、不改字节内容**

## 附录 A：GPU 卡死 / 跑出大量空白（Windows TDR 超时）

> **不是软件坏了，是 Windows 的一条规则把显卡「误杀」了。**

Windows 有个「GPU 超时看门狗」（**TDR**）：只要显卡单个任务超过 **2 秒**没算完，系统就以为显卡死机了，**强制把显卡驱动重启一次**。驱动一重启，OCR 引擎手里的显卡就永久失效——**程序还在跑、界面也不报错，但每一页都算不出文字**，于是输出一堆空白。

**两个动作就能解决（建议都做）：**

1. **双击本目录的 `GPU卡死修复_调大TDR超时_需重启.reg`** → 弹窗点「是」→ **重启电脑**。这把 2 秒放宽到 8 秒。（反悔了？双击 `GPU卡死修复_还原TDR超时_需重启.reg` 再重启即可。）
2. **把「精度」改成 `FP16 (快速)`**（用 ncnn Vulkan 引擎时）。单次计算量大幅减少，更不容易撞上 2 秒线。**AMD 核显请保持 FP32。**

等价的注册表手工命令：

```
reg add "HKLM\SYSTEM\CurrentControlSet\Control\GraphicsDrivers" /v TdrDelay    /t REG_DWORD /d 8 /f
reg add "HKLM\SYSTEM\CurrentControlSet\Control\GraphicsDrivers" /v TdrDdiDelay /t REG_DWORD /d 8 /f
```

> **实测本机 TDR 相关键全部未设置**，即 Windows 默认的 **2 秒**，所以直接补上即可。
> 副作用：万一显卡真的挂了，桌面最多卡 8 秒才恢复（原来 2 秒）——仅此而已。
>
> **换驱动不能保证解决**：TDR 是 Windows 的机制，与驱动版本无关。实测本机驱动 **610.74** 已是 RTX 5060 的适配版本，引擎确实跑在 `Vulkan device 1: NVIDIA GeForce RTX 5060`（r-score 76，远高于 AMD 核显的 21），**不存在「驱动装错 / 跑错卡」**。
>
> **v1.3.4 起程序还有兜底**：万一真撞上，会自动重建引擎 + 重跑本页，**绝不把「算不出来」当成「这页没字」交给你**。日志里看到 `[自动恢复]` 开头的行，就是在自动恢复，不用管它。
